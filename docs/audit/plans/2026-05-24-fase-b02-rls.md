# Fase B2 — RLS Multi-tenancy (Implementation Plan)

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development.

**Goal:** Auditar RLS multi-tenancy de TurnoGol para detectar y cerrar gaps NO cubiertos por los 96 isolation tests existentes que pasan en B0. Foco: WITH CHECK en INSERT/UPDATE (gap potencial P0 según mapeo), service role bypass via `getSql()`/`getDb()` directo, pool poisoning, Realtime client real, audit system_admins. Resultado: leak entre tenants imposible incluso con JWT forjado o uso incorrecto de la DB API.

**Architecture:** Auditoría dirigida por hipótesis del mapeo de investigator. Cada task = test específico de gap, si pasa = validado, si falla = bug + fix + re-test. Worktree `audit/backend-b02`.

**Tech Stack:** Vitest, Drizzle, postgres.js, Supabase RLS, JWT.

## Task 5: Pool poisoning test

- [ ] **Step 1**: Simular escenario:
  - Request 1 (admin tenant A) ejecuta withTenantContext y termina
  - Request 2 (admin tenant B) ejecuta withTenantContext en MISMA conexión del pool
  - Validar que request 2 NO ve datos de A

Test fuerza pool reuse (max 1 conexión + Promise.all).

## Task 6: Realtime con cliente Supabase real

- [ ] **Step 1**: Instanciar Supabase client con JWT de admin tenant A.
- [ ] **Step 2**: Subscribe a `bookings` table.
- [ ] **Step 3**: Otro admin tenant B inserta booking.
- [ ] **Step 4**: Validar que A NO recibe evento del booking de B.

## Task 7: JWT forgery defense

- [ ] **Step 1**: Generar JWT con tenant_id de tenant B, pero firmado con secret válido (simulando attacker con acceso al secret o token mal validado).
- [ ] **Step 2**: Llamar a endpoints admin con ese JWT.
- [ ] **Step 3**: Validar que endpoints rechazan o filtran a tenant B (lo cual implica que el endpoint NO verifica tenant_id contra DB, solo lee del JWT).

Nota: si app confía en JWT app_metadata, NO hay defensa adicional. Riesgo: si Supabase auth.jwt key se filtra → leak total. Mitigación: validar tenant_id contra DB en cada request o usar Supabase como SoR.
