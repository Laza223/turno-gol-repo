## 0. Bloqueante encontrado antes de poder ejecutar esto

`LAUNCH.md` (commit `2a49379`, hoy) declara que Staging **REQUIERE** un proyecto Supabase dedicado, separado de
producción — deprecando el modelo anterior (Vercel Preview compartiendo DB con prod). Pero al revisar
`docs/audit/STATE.md` ese proyecto separado todavía figuraba como diferido a v1.5 (corregido en este mismo cambio,
ver §7). No hay ningún project ref ni connection string de un Supabase de staging real committeado en el repo
(`.env.staging.example` solo trae placeholders `xxx`; `.env.staging` real no existe o está gitignored).

**Consecuencia:** los comandos de abajo son correctos y reproducibles, pero no se pueden correr contra un
"Staging real" hasta que `STAGING-001` (provisioning del proyecto Supabase de staging) esté cerrado con un project
ref concreto. Sin eso, este drill no cierra el done-criterion de negocio — solo lo deja listo para ejecutar en
cuanto exista el project ref.

## 1. Prerrequisitos

```bash
# Supabase CLI (v1.x+) instalado y logueado
npx supabase --version
npx supabase login   # o SUPABASE_ACCESS_TOKEN en env para uso no interactivo

# Cliente Postgres nativo (para el path pg_dump/pg_restore de formato custom, §3 opción B)
pg_dump --version
pg_restore --version
psql --version

# Variables de entorno de esta corrida (completar con los valores reales)
export STAGING_PROJECT_REF="xxxxxxxxxxxxxxxxxxxx"          # Supabase Dashboard → Settings → General → Reference ID
export STAGING_DATABASE_URL="postgresql://postgres:[PASSWORD]@db.${STAGING_PROJECT_REF}.supabase.co:5432/postgres"
export SUPABASE_ORG_ID="xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"  # Dashboard → org settings, o `supabase orgs list`
export DRILL_DATE="$(date +%Y%m%d_%H%M%S)"
```

> `STAGING_DATABASE_URL`: Dashboard del proyecto de staging → Settings → Database → Connection string → URI
> ("Direct connection", no el pooler — necesario para `pg_dump`/`pg_restore`).

## 3. Backup manual

### Opción A — Supabase CLI (recomendada, pedida para este drill)

```bash
# Dump completo (schema + data), SQL plano
npx supabase db dump \
  --db-url "$STAGING_DATABASE_URL" \
  -f "backup_turnogol_staging_${DRILL_DATE}.sql"

# Dump solo-datos (más rápido para comparar/diffear, no recrea schema)
npx supabase db dump \
  --db-url "$STAGING_DATABASE_URL" \
  --data-only \
  -f "backup_turnogol_staging_data_${DRILL_DATE}.sql"
```

> Requiere Docker corriendo localmente — `supabase db dump` levanta un contenedor con la versión de `pg_dump`
> compatible con el server de Supabase. Si Docker no está disponible, usar Opción B.

### Opción B — `pg_dump` directo, formato custom (permite restore selectivo por tabla, §5)

```bash
pg_dump "$STAGING_DATABASE_URL" \
  --format=custom \
  --no-owner \
  --no-acl \
  --exclude-schema=pgboss \
  --file="backup_turnogol_staging_${DRILL_DATE}.dump"
```

`--exclude-schema=pgboss` excluye los jobs en cola (se recrean solos, no forman parte de los datos de negocio).

### Verificar el backup

```bash
# Opción A (SQL plano)
head -50 "backup_turnogol_staging_${DRILL_DATE}.sql"
grep -c "^INSERT INTO" "backup_turnogol_staging_${DRILL_DATE}.sql"

# Opción B (custom format)
pg_restore --list "backup_turnogol_staging_${DRILL_DATE}.dump" | head -30
```

Guardar el archivo fuera del laptop/servidor que corrió el dump (Drive/S3) con nombre `backup_turnogol_staging_<fecha>_drill.{sql,dump}`.

## 4. Crear proyecto temporal (destino del restore)

**Nunca restaurar/destruir sobre el proyecto de staging real.** El "desastre simulado" ocurre en un proyecto
descartable, aparte.

```bash
npx supabase projects create "turnogol-staging-drill-${DRILL_DATE}" \
  --org-id "$SUPABASE_ORG_ID" \
  --db-password "$(openssl rand -base64 24)" \
  --region sa-east-1 \
  --plan free

# Anotar el project ref que devuelve el comando anterior:
export TEMP_PROJECT_REF="xxxxxxxxxxxxxxxxxxxx"
export TEMP_DATABASE_URL="postgresql://postgres:[PASSWORD]@db.${TEMP_PROJECT_REF}.supabase.co:5432/postgres"
```

Alternativa Dashboard: New Project → misma región que staging → plan Free alcanza para el drill (no necesita PITR).

## 5. Restaurar (baseline) → simular desastre → restaurar (recovery)

```bash
# 5.1 — Restore baseline: probar que el backup restaura limpio
psql "$TEMP_DATABASE_URL" -f "backup_turnogol_staging_${DRILL_DATE}.sql"
# — o, con el dump formato custom (Opción B):
pg_restore --dbname="$TEMP_DATABASE_URL" --no-owner --no-acl --clean --if-exists \
  "backup_turnogol_staging_${DRILL_DATE}.dump"

# 5.2 — Verificar baseline: counts deben matchear el snapshot de §2
psql "$TEMP_DATABASE_URL" -c "
  SELECT 'tenants' t, count(*) FROM tenants
  UNION ALL SELECT 'courts', count(*) FROM courts
  UNION ALL SELECT 'bookings', count(*) FROM bookings
  UNION ALL SELECT 'payments', count(*) FROM payments;"

# 5.3 — SIMULAR DESASTRE (solo contra $TEMP_DATABASE_URL, jamás $STAGING_DATABASE_URL)
psql "$TEMP_DATABASE_URL" -c "DROP TABLE IF EXISTS bookings CASCADE;"

# 5.4 — Confirmar que está roto
psql "$TEMP_DATABASE_URL" -c "SELECT count(*) FROM bookings;"
# Esperado: ERROR:  relation "bookings" does not exist

# 5.5 — RECOVERY: restaurar de nuevo desde el mismo backup (recovery real, no solo baseline)
#        Con dump custom se puede restaurar solo la tabla afectada (restore selectivo, más rápido):
pg_restore --dbname="$TEMP_DATABASE_URL" --no-owner --no-acl --clean --if-exists \
  --table=bookings \
  "backup_turnogol_staging_${DRILL_DATE}.dump"
#        Con dump SQL plano (Opción A) no hay restore selectivo — reaplicar el dump completo:
psql "$TEMP_DATABASE_URL" -f "backup_turnogol_staging_${DRILL_DATE}.sql"

# 5.6 — Confirmar recovery
psql "$TEMP_DATABASE_URL" -c "SELECT count(*) FROM bookings;"
# Esperado: mismo count que §5.2 / baseline de §2
```

Cronometrar desde el inicio de 5.3 (momento del "desastre") hasta la confirmación en 5.6 — ese intervalo es el RTO
medido (§6).
